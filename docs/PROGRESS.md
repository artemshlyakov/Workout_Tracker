# Прогресс Workout Tracker

## Текущий этап

Plan 003B — рабочая ветка `feat/plan-003b-auth-sync`, [Draft PR #5](https://github.com/artemshlyakov/Workout_Tracker/pull/5). PR #3 и PR #4 уже объединены в `main`; эта ветка создана от актуального `main`. Ветку не объединять до ревью закрытого пилота.

## Реализовано

- Подключён официальный `@supabase/supabase-js` с зафиксированной версией и только публичным publishable key.
- Экран входа, контролируемая регистрация по `?signup=1`, восстановление сеанса, выход, показ email и AuthGate. Регистрация дополнительно управляется настройкой Supabase Auth; параметр URL сам по себе никого не регистрирует.
- Разделены состояния `SIGNED_OUT`, `SIGNED_IN_ONLINE`, `SIGNED_IN_OFFLINE_CACHED`, `AUTH_RECHECK_REQUIRED`. Без входа журнал не виден; первый офлайн-вход на новом устройстве закрыт.
- Локальный workspace и отдельная база IndexedDB создаются по стабильному user ID. Тестовые данные Plan 002 не переносятся в личный аккаунт. При выходе с очередью изменений есть предупреждение, записи остаются за прежним владельцем.
- Для нового устройства реализована первоначальная загрузка четырёх пользовательских таблиц. Новая пустая учётная запись получает локальную тренировку без тестовых подходов.
- Изменения отправляются через `apply_workout_operation`: UUID сохраняется при повторе, родители отправляются раньше дочерних записей, CAS revision и tombstones учитываются, конфликт или ошибка сохраняют outbox. Перед отправкой проверяется текущий Auth user и owner каждой операции; запрос получает JWT именно проверенного владельца.
- После внешнего ревью PR #5 статус облака разделён на проверку, синхронизацию, подтверждение, ожидание и ошибку. Пустая очередь сама по себе не означает подтверждения: оно показывается только после успешного первоначального pull или ответа RPC для всех ожидавших операций. Ошибки, черновик и статус привязаны к компоненту конкретного аккаунта и сбрасываются при A/B-переключении.
- При выходе/смене аккаунта запросы предыдущего владельца прерываются; неопределённо завершённые операции остаются в его IndexedDB для повторной отправки с прежним UUID. Отмена удаления создаёт новый подход с новым UUID, поэтому подтверждённый tombstone не превращается в конфликт восстановления.
- Есть экспорт личных данных в JSON. Импорт личного экспорта и разрешение конфликтов пока не реализованы.
- Локально открыта production-сборка и сделаны снимки в 360 × 800 и 390 × 844. На обеих ширинах нет горизонтальной прокрутки, ошибок страницы не обнаружено. Публичный `github.io` недоступен из этой среды из-за сетевой политики; его фактическую работу не подтверждаем.

## Ограничения и контрольные точки

1. В Supabase Dashboard для закрытого пилота проверить email/password, временно разрешить регистрацию и выключить `Confirm Email`. Владелец регистрируется сам по адресу приложения с `?signup=1`, затем выключает `Allow new users to sign up` на сервере. Настройки Auth недоступны имеющимся инструментам.
2. Для публичного Pages в Settings → Pages → Build and deployment установить Source: **GitHub Actions**. PR #4 уже добавил workflow, публикующий `dist`; при Source `Deploy from a branch` GitHub запускает старую Jekyll-публикацию корня `main`, где исходный TypeScript браузером не исполняется. Настройку Pages здесь изменить или прочитать не удалось.
3. После двух контролируемых тестовых аккаунтов выполнить `supabase/tests/security.integration.mjs` для A/B/anon и ручные тесты входа, выхода, смены аккаунта и синхронизации на настоящем Pages URL.
4. Текущая синхронизация делает первоначальный pull для нового устройства и push локальной очереди. Поздние изменения с другого устройства, автоматическое разрешение конфликтов, полный импорт личного экспорта и release-gate относятся к следующему этапу; до их проверки не использовать приложение как единственную копию реального дневника.
