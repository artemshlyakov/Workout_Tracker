Воспроизводится `scripts/check-diary-browser.py` с локальным dev-сервером и Python Playwright/Chromium. Это реальный Dexie с тестовым owner, **не тест Supabase Auth/REST в браузере**.
- Финальные локальные проверки: lint, typecheck, 57 тестов, build и diff --check прошли; npm audit --omit=dev — 0 уязвимостей. Production PWA shell открывается после offline reload с сохранением экрана входа (Chromium 390 px). Каталог образует chunk 848 kB / 164 kB gzip; предупреждение Vite о размере известно, precache приложения ~1,5 MB; 17,8 MB изображений не входят в precache.
- Существующие реальные API/Auth/RLS/CAS и адаптерные интеграционные результаты Plan 003B сохранены ниже. Новые тестовые аккаунты не создавались, удалённые пароли не требовались. Полный браузерный Auth/offline/online gate и физический iPhone остаются непроверенными в Codex.

## Предыдущий этап (историческая запись)

PR #5 (Auth и начальная синхронизация) и PR #6 (навигация, история, каталог, базовый прогресс) объединены в `main`. Ветка `feat/multi-exercise-workouts` добавляет полный ввод силовой тренировки с несколькими упражнениями без изменения SQL/RLS или Dexie-схемы. Этот этап не закрывает release gate Plan 004.

Новый личный workspace пуст: название задаётся до начала тренировки, а упражнения выбираются или создаются пользователем. Ранее сохранённые тренировки и outbox остаются в прежних таблицах и читаются без миграции. Dev-only локальный профиль сохраняет старый пример для совместимости с резервными копиями.

## Реализовано

- Подключён официальный `@supabase/supabase-js` с зафиксированной версией и только публичным publishable key.
- Экран входа, контролируемая регистрация по `?signup=1`, восстановление сеанса, выход, показ email и AuthGate. Регистрация дополнительно управляется настройкой Supabase Auth; параметр URL сам по себе никого не регистрирует.
- Разделены состояния `SIGNED_OUT`, `SIGNED_IN_ONLINE`, `SIGNED_IN_OFFLINE_CACHED`, `AUTH_RECHECK_REQUIRED`. Без входа журнал не виден; первый офлайн-вход на новом устройстве закрыт.
- Локальный workspace и отдельная база IndexedDB создаются по стабильному user ID. Тестовые данные Plan 002 не переносятся в личный аккаунт. При выходе с очередью изменений есть предупреждение, записи остаются за прежним владельцем.
- Для нового устройства реализована первоначальная загрузка четырёх пользовательских таблиц. Новая пустая учётная запись получает пустой локальный workspace без тренировки и тестового упражнения.
- Изменения отправляются через `apply_workout_operation`: UUID сохраняется при повторе, родители отправляются раньше дочерних записей, CAS revision и tombstones учитываются, конфликт или ошибка сохраняют outbox. Перед отправкой проверяется текущий Auth user и owner каждой операции; запрос получает JWT именно проверенного владельца.
- После внешнего ревью PR #5 статус облака разделён на проверку, синхронизацию, подтверждение, ожидание и ошибку. Пустая очередь сама по себе не означает подтверждения: оно показывается только после успешного первоначального pull или ответа RPC для всех ожидавших операций. Ошибки, черновик и статус привязаны к компоненту конкретного аккаунта и сбрасываются при A/B-переключении.
- При выходе/смене аккаунта запросы предыдущего владельца прерываются; неопределённо завершённые операции остаются в его IndexedDB для повторной отправки с прежним UUID. Отмена удаления создаёт новый подход с новым UUID, поэтому подтверждённый tombstone не превращается в конфликт восстановления.
- Есть экспорт личных данных в JSON. Импорт личного экспорта и разрешение конфликтов пока не реализованы.
- Первоначальный pull может содержать удалённую тренировку с tombstone рядом с действующей. Локальный репозиторий теперь выбирает действующую тренировку вместе с её связью и подходами; изменение названия и добавление подхода адресуют ту же запись.
- PR #6 объединил мобильные экраны истории, каталога и базового прогресса. Новый ввод нескольких упражнений проверен в локальном Chromium на 360 и 390 px: три упражнения, сохранение подходов, завершение, перезагрузка, история, отсутствие горизонтальной прокрутки и ошибок страницы. Снимки: `docs/screenshots/workout-multi-{360,390}.png`. Эта локальная проверка не подтверждает облачный Auth/offline/online сценарий.

## Проверки

- Для текущего этапа: `npm run lint`, `npm run typecheck`, `npm test -- --run` (41 тест), `npm run build`, `git diff --check` прошли локально. Регрессии покрывают три упражнения, отдельные подходы, повторное открытие Dexie, завершение, сохранение очереди, атомарность записи и совместимость старого dev backup. Новые облачные интеграционные тесты не запускались; ранее выполненные результаты PR #5 сохраняются.

- 22 октября 2026 владелец временно открыл регистрацию при `Confirm Email OFF`; `auth-pilot.mjs signup` создал ровно два контролируемых аккаунта A/B. После немедленного закрытия регистрации серверный Auth API подтвердил `disable_signup=true`, `mailer_autoconfirm=true`, Email provider ON. Фаза `verify` подтвердила вход A/B и отказ нового signup.
- Реальный `security.integration.mjs` прошёл: A/B/anon, видимость четырёх пользовательских таблиц, закрытый ledger, запрет прямого REST INSERT/UPDATE/DELETE, чужой RPC и FK, повтор операции, CAS/conflict и tombstones. Первоначальная версия теста послала несуществующее поле `revision` в PATCH закрытого ledger и остановилась на HTTP 400 до проверки прав; поле тестового запроса исправлено, полный повтор прошёл. SQL/RLS/миграции в облаке не менялись.
- Реальный `sync.integration.ts` через Supabase Auth, CloudSync и локальный Dexie-адаптер прошёл: A/B local scope, запрет отправки A с JWT B, push названия/подхода, локальная очередь и повторное открытие базы, отправка после восстановления связи, первоначальный pull в чистую локальную базу. Офлайн-поведение проверено на уровне адаптеров с `fake-indexeddb`, не как полный браузерный сценарий.
- Chromium открыл локальную production-сборку без входа на 360 × 800 и 390 × 844: форма входа, закрытая регистрация, отсутствие горизонтальной прокрутки и ошибок страницы. Браузерный вход заблокирован TLS-проверкой proxy (`ERR_CERT_AUTHORITY_INVALID`). Окружение разрешает HTTPS через proxy и не даёт прямой TCP-маршрут к Supabase. OpenSSL подтвердил цепочку через предоставленный CA proxy; временный профиль Chromium с системным verifier всё равно отверг сертификат. Автоматическое согласование отклонило постоянное добавление CA в хранилище доверия Chromium. Владелец запретил это изменение и обход проверки TLS; дальнейших попыток установки CA не было.
- Для Node 24 требуется `NODE_USE_ENV_PROXY=1`, чтобы `fetch` использовал настроенный HTTPS proxy. Пароли A/B были только во временном файле `/tmp` с правами `0600`; по завершении доступных проверок файл удалён командой `auth-pilot.mjs cleanup`, отсутствие файла подтверждено. Облачные аккаунты и записи сохранены; JWT не печатались. Для браузерного теста владельца подготовлен `docs/operations/plan-003b-browser-check-windows.md` с аккаунтами под его контролем.
- Автотесты покрывают входные состояния, owner-scoped доступ, стартовую загрузку и повтор после её ошибки, порядок RPC, повтор с тем же UUID/CAS, сохранение конфликта, A/B-переключение и выход, позднее восстановление сеанса, остановку незавершённого запроса, привязку JWT и отмену быстрого/подтверждённого удаления.
- Регрессионный тест проверяет выбор действующей тренировки при наличии tombstone. При финальной проверке 23 октября 2026 повторно прошли `npm run lint`, `npm run typecheck`, `npm test -- --run` (43 теста), `npm run build` и `git diff --check`. Vite предупредил о JS chunk >500 kB; сборка завершилась успешно. GitHub Actions run `39767182834` для коммита `3ee10c1` завершился успешно (build; deploy пропускается для Draft PR).
- GitHub Pages API сообщает `build_type=workflow`, `status=built`; workflow для merge-коммита `1ac0d38` завершился успешно, публичный URL вернул HTTP 200. Это проверка доступности текущего `main`, а не браузерного входа или синхронизации.

## Ограничения и контрольные точки

1. Регистрация тестовых A/B завершена и снова закрыта сервером. Аккаунт владельца с реальным email ещё не создавался; для него потребуется отдельное контролируемое окно регистрации после ревью. Настройки Auth в Dashboard меняет владелец.
2. Pages Source подтверждён через GitHub API как workflow; объединённый `main` публикуется через Actions. Браузерный Auth/offline/online сценарий на Pages ещё не проверен. Изменения этой ветки до объединения не опубликованы на Pages.
3. Полный браузерный сценарий входа/выхода, локального IndexedDB, офлайн и повторного подключения, переключения A/B и экспорта ещё не подтверждён. В основной среде Chromium не доверяет сертификату proxy для Supabase; постоянное изменение доверия было отклонено автоматической проверкой и запрещено владельцем. Изолированный временный Chromium смог открыть приложение и установить защищённое соединение с Auth API, но после удаления тестовых паролей A/B полный сценарий не запускался. Выполнить сценарий на Windows по `docs/operations/plan-003b-browser-check-windows.md` с контролируемыми аккаунтами. Новые A/B для повторения уже завершённых API-проверок не создавать.
4. Текущая синхронизация делает первоначальный pull для нового устройства и push локальной очереди. Поздние изменения с другого устройства, автоматическое разрешение конфликтов, полный импорт личного экспорта и release-gate относятся к следующему этапу; до их проверки не использовать приложение как единственную копию реального дневника.
