# Auth architecture — Workout Tracker v0.5

**Принято:** обязательная авторизация Supabase Auth; **для закрытого личного пилота — email + пароль без подтверждения почты (ADR 0007)**. Не путать с публично открытой регистрацией. ADR 0006 определяет приватность аккаунтов; ADR 0007 задаёт временный режим onboarding и отказ от SMTP на старте.

## Жизненные циклы аккаунта
1. **Первое подключение онлайн:** администратор проекта временно разрешает регистрацию, выключает `Confirm Email` в Authentication → Providers → Email, владелец регистрируется с реальным email и сильным паролем. Supabase создаёт user ID и session сразу; email *не верифицирован фактически*.
2. **Закрыть самостоятельные регистрации:** после первого аккаунта администратор **выключает `Allow new users to sign up`**. Уже созданный пользователь по-прежнему может входить, а посторонние — нет. Проверять это не только UI, но и непосредственно через Supabase Auth. Кнопка регистрации в UI управляется локальной настройкой отображения, которая не является защитой.
3. **Вход:** `signInWithPassword({ email, password })` через auth adapter, не в UI-компоненте. Пароли никогда не сохраняются в пользовательских таблицах и не логируются.
4. **Выход:** если есть pending записи — предупредить и предложить sync/export; UI сразу закрывает чужой кеш, не переносит операции в новый аккаунт.
5. **Офлайн:** разрешить доступ лишь после ранее успешного входа именно этого user ID на данном устройстве, если пользователь явно не выходил. Нет первого входа без сети; при её возвращении подтвердить актуальную session до sync.

## Состояния интерфейса
- `SIGNED_OUT`: вход и сообщение, что для первого входа нужен интернет; личные данные недоступны.
- `SIGNED_IN_ONLINE`: локальный workspace по `auth.uid()`, фоновые загрузки и отправка допустимы.
- `SIGNED_IN_OFFLINE_CACHED`: локальная запись/история, отправка в Supabase приостановлена. Не выдавать это за криптографическую защиту от человека с доступом к разблокированному устройству.
- `AUTH_RECHECK_REQUIRED`: pending данные сохранены за прежним владельцем, отправка блокирована до проверки сессии.

## Экраны пилота
- Вход: email, пароль, показать/скрыть, статус сети/ошибки, `Войти`.
- Регистрация (только на этапе onboarding): email, пароль, подтверждение пароля, предупреждение `Почта не проверяется; восстановление пароля пока недоступно`.
- При закрытом signup: вместо рабочей регистрации сообщение `Регистрация временно закрыта`.
- Профиль: email (отображение), выход, экспорт истории; опционально смена пароля при действующей сессии по правилам SDK.
- **Не делать фиктивные экраны** подтверждения адреса/«Забыли пароль?». Отдельный этап после SMTP/OAuth и актуализированного ADR.

## Безопасность и архитектура
- `user_id` всегда равен проверенному `auth.uid()`; все личные таблицы закрыты RLS+grants; тесты A/B/anon, включая forged foreign keys.
- Клиент видит только publishable key и URL Supabase. Никогда `service_role`, SMTP secrets, пароль пользователя или служебные токены в GitHub Pages/`VITE_*`.
- Работать через `src/data/auth` / `src/data/cloud` и порты, не вызывать SDK непосредственно из произвольных экранов.
- `supabase-js` обслуживает сессии; никакого собственного хранилища паролей и самодельного JWT.
- Тесты: успешная регистрация при открытом signup; отсутствие email-письма; вход; отключение signup и невозможность новой регистрации; повторный вход A; негативные проверки B/anon; logout и кеш; офлайн и повторная синхронизация.
- Для публичного запуска на других пользователей: согласовать восстановление и подтверждение адреса, сценарий ранее auto-confirmed email, защиту от abuse (CAPTCHA и лимиты) и протестировать redirects на Pages.
