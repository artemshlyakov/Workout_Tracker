# ADR 0006 — Обязательная авторизация и приватные аккаунты

**Статус: ACCEPTED (2026-10-20, запрос владельца продукта).**

**Дополнение:** ADR 0007 разрешает email+password без подтверждения только в закрытом личном пилоте при отключении последующих регистраций. Открытая регистрация по-прежнему требует отдельного решения.

## Контекст
Публичная ссылка GitHub Pages должна позволять любому человеку создать собственный аккаунт и вести **свою** историю тренировок, но не читать или менять данные владельца. Авторизация должна работать вместе с offline-first записью.

## Решение
1. В **публичном релизе** экран входа обязателен. Доступ к персональным данным только после установки идентичности. Публичное приложение не имеет пользовательского «гостевого дневника».
2. Основной запланированный метод: **email + password**, реализованный Supabase Auth; имя пользователя (`display_name`) необязательно и не является ключом безопасности. Никогда не хранить пароли в своих таблицах.
3. Для **открытых публичных регистраций** с проверкой email и сбросом пароля требуется **проверенный SMTP**: стандартный отправитель Supabase ограничен адресами участников организации и 2 письмами/час. Использовать сторонний провайдер с бесплатным тарифом только после проверки лимитов и условий. Если бесплатный SMTP недоступен — альтернативный UX: Google OAuth через Supabase, без отключения email-verification. Окончательный провайдер подтверждается при Plan 003.
4. Каждая запись в Supabase принадлежит стабильному `auth.uid()`; RLS и grants ограничивают select/insert/update/delete, в том числе по вложенным FK; тестировать User A, User B и anon. UI-скрытие разделов не является мерой безопасности.
5. На устройстве локальные записи разделены по user ID. До первой успешной авторизации онлайн нельзя открыть **личный** журнал. После выполненного входа приложение может работать офлайн с **ранее установленной идентичностью на том же устройстве**; при истекшей или непроверенной сессии отправка в облако приостановлена до повторной онлайн-проверки.
6. При явном выходе скрыть пользовательские данные и не разблокировать их офлайн до повторного входа; если есть pending-записи, прежде предупредить, предложить синхронизировать либо безопасно экспортировать. Нельзя отправлять данные через следующую учётную запись. Стратегию хранения/удаления локального кэша после выхода подробно согласовать и тестировать, приоритет — избежать утечек и потери несинхронизированных данных.
7. В Plan 002 допустим **только локальный тестовый профиль разработчика** для проверки IndexedDB/PWA без подключённого Supabase, с видимой пометкой тестового режима. Он не публикуется как общедоступный продукт и не мигрирует автоматически в облачные аккаунты.
8. До успешного завершения Plan 004 продукт не рекламируется как готовый приватный дневник тренировок.

## Последствия
+ Независимые аккаунты, несколько устройств и контролируемая граница доступа.
+ Меньше риска смешивания локальных записей между пользователями.
− Потребуется настройка email-доставки/провайдера авторизации, redirects и дополнительные тесты офлайн-сценариев.
− Отдельно решить, какой способ входа окончательно использовать в общедоступной версии, чтобы сохранить требование «без оплаты».
