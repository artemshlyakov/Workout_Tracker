# ADR 0007 — Email + password без подтверждения для закрытого личного пилота

**Статус: ACCEPTED, 2026-10-20.** Дополняет ADR 0006 (обязательные приватные аккаунты), временно уточняет требования к письмам для **закрытого личного пилота**. **Не отменяет** RLS, проверку сессий, ограничения офлайн-доступа и требование не публиковать персональные данные.

## Контекст
Один владелец будет первым пользователем. Публичное создание аккаунтов, подтверждение email, SMTP и восстановление пароля сейчас непропорционально усложняют запуск бесплатного MVP. Однако вход и разграничение данных разных пользователей остаются обязательными.

## Решение
1. Использовать Supabase Auth `email + password` с настройкой **Confirm Email = OFF** на этапе закрытого личного пилота. Supabase помечает адрес как подтверждённый **без проверки владения**; это технический компромисс, а не верификация человека.
2. Владелец создаёт аккаунт **с реальным доступным email**, сильным уникальным паролем (рекомендовано 12+ символов, менеджер паролей); вымышленные и чужие адреса **не рекомендуются**. Проверить вход/выход/повторный вход.
3. **После регистрации владельца отключить `Allow new users to sign up` в настройках Supabase Auth.** Существующие аккаунты продолжают входить. При закрытой регистрации UI показывает `Регистрация временно закрыта`, а сервер всегда является источником истины. Клиентский флаг отображения ссылки не заменяет настройку сервера.
4. Пока SMTP не настроен, **не обещать** email verification и восстановление пароля: не показывать функциональную кнопку `Забыли пароль?`, ведущую в неработающий процесс. В профиле можно запланировать смену пароля для уже вошедшего пользователя. При утрате пароля после выхода предусмотренных пользовательских механизмов восстановления пока нет.
5. Для тестирования изоляции A/B/anon временно открывать регистрацию, создать тестовый аккаунт B под контролируемым адресом и снова закрывать. Никаких общих паролей в репозитории или скриншотах.
6. План 001 и 002 не меняется: демо UI и локальный тестовый режим. Реальная настройка Supabase — в Plan 003. Plan 004 становится **gate для закрытого личного пилота**, а не для открытого массового запуска.
7. **Перед открытием регистрации сторонним пользователям:** отдельно принять новый ADR о способе проверки личности/восстановления (рабочий SMTP с подтверждением и безопасным обслуживанием существующих аккаунтов, либо OAuth), защите от злоупотреблений и процедурах поддержки. Учесть, что ранее автоматически подтверждённые email **не становятся реально проверенными** задним числом.

## Риски и смягчение
- Не подтверждается владение email; в открытой регистрации возможны захват адреса и социальная инженерия. => Регистрация закрыта после onboarding владельца; позже верификация/OAuth.
- Пароль утрачен/забыт, SMTP нет. => Менеджер паролей, реальный email на будущее, локальная и облачная история + регулярный JSON-экспорт; не имитировать восстановление.
- Открытый URL GitHub Pages видят все. => AuthGate, Supabase RLS+grants, негативные тесты прямого API для A/B/anon; скрытие кнопок UI недостаточно.
- Безопасность офлайн-содержимого на устройстве не абсолютна. => Изоляция по `auth.uid()`, скрытие после выхода, запрет cross-user sync, ясные предупреждения.
