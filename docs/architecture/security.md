# Security and privacy — v0.5

## Threat model / trust boundaries
Ссылка на GitHub Pages открывает только публичный код/интерфейс. Данные должны быть изолированы Supabase Auth + PostgreSQL RLS и grants, не условием в React. IndexedDB не считается криптографически защищённым хранилищем: на разблокированном/скомпрометированном устройстве есть дополнительный риск доступа к локальной информации.

## Auth (ADR 0006)
- Закрытый личный пилот требует авторизации email+password. Confirm Email OFF означает **непроверенную почту**; регистрация доступна только для создания контролируемого аккаунта владельца, затем `Allow new users to sign up OFF` **на сервере**. Публичные регистрации/confirmation/reset до отдельного решения по проверенной доставке или OAuth запрещены.
- Первый вход и регистрация онлайн; офлайн — только существующая локальная область **ранее аутентифицированного и не вышедшего** пользователя.
- После sign-out личные данные скрыты, cached account не считается вошедшим. Pending-записи не отправляются через другого пользователя и не удаляются без информированного действия.
- Не хранить пароль самостоятельно; использовать Supabase SDK для session handling. Не отдавать access/refresh tokens в PWA SW cache или собственные логи.

## Secrets / deployment
- Браузеру допустимы `VITE_SUPABASE_URL` и publishable key, но **никогда** Supabase secret/service_role, SMTP password, SQL connection string или другие ключи с повышенными правами.
- Проверить `.gitignore`, `.env.example` и собранный GitHub Pages bundle на секреты.
- Не публиковать личные тренировки в repo или fixtures; не записывать пароли, email, токены и персональные данные в telemetry/logs.

## Database authorization
- Включить RLS для каждой публично доступной таблицы, отозвать ненужные grants у `anon`, проверить предоставленные операции для `authenticated`.
- Все user-owned сущности имеют `user_id = auth.uid()` и owner-aware FK, включая workout_exercises и sets; запрещены ссылки на чужие родительские строки.
- Тесты A/B/anon на SELECT, INSERT, UPDATE, DELETE и попытки создать cross-account связи; прямые REST запросы тоже должны быть отклонены.
- Чувствительные записи через контролируемый RPC с серверной проверкой owner + CAS revision + idempotent operation ledger; самописный RPC не должен обходить защиту. Security definer крайне осторожно, фиксировать `search_path`, ограничить EXECUTE.

## Backups
- Индивидуальные JSON экспорт/импорт, валидировать owner и version. Очистка браузерного хранилища может удалить офлайн-записи; предупреждать об unsynced изменениях до logout.
- Бесплатный облачный проект не является абсолютной гарантией сохранения при блокировке/паузе/удалении; экспорт необходим.

## Checks
- A видит/меняет только A. B видит/меняет только B. anon не читает/создаёт приватные записи.
- После явного выхода локальная история не отображается, включая offline.
- Временная недоступность Auth не уничтожает pending; реальная синхронизация только после подтверждения пользователя.
- В пилоте тестируются регистрация владельца, вход, запрет последующих signup, отсутствие ложного reset, AuthGate и доступ на Pages. Перед открытой регистрацией — отдельный gate verification/recovery/anti-abuse.
