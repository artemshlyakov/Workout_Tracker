# Plan 004 — reliable offline sync + **closed personal pilot** release gate

**Status: IN PROGRESS after Plan 003B.** В личный пилот выходить только после перечисленных проверок. **Не открывает публичную регистрацию сторонним пользователям.**

По запросу владельца первым видимым срезом добавляются мобильные окна истории, упражнений и базового прогресса из сохранённых записей. Это не заменяет перечисленные ниже release blockers. Графики и расширенная аналитика Plan 005 остаются отдельной задачей.

## Исходная точка после Plan 003B

Существуют AuthGate, отдельная IndexedDB на user ID, атомарные локальные запись/outbox, первоначальный pull четырёх таблиц, последовательный push через `apply_workout_operation`, серверные CAS/ledger/tombstones, остановка sync при смене аккаунта и личный JSON-экспорт. Реальные Auth, REST/RPC, RLS и интеграционные проверки адаптеров прошли. Пароли тестовых A/B удалены. Полный браузерный Auth/offline/online сценарий и запуск версии PR на Pages не подтверждены; не повторять завершённые API-проверки без конкретной причины.

## Порядок реализации

1. **Очередь и восстановление доставки.** На базе `CloudSync` и `DexieWorkoutRepository` добавить повтор по событиям online/foreground, ручную кнопку синхронизации, ограниченный exponential backoff с jitter и видимые pending/error/confirmed состояния. Сохранить неизменными `operationId`, payload и `baseServerRevision` после неопределённого ответа. Покрыть падение после server commit до локального ack, несколько правок одной записи, порядок родителей и дочерних записей, перезапуск приложения и смену аккаунта.
2. **Получение изменений с другого устройства.** Расширить текущий `prepare()` (он загружает облако только при отсутствии workspace) до безопасного повторного pull по владельцу. Определить курсор/ревизии и атомарное применение удалённых записей, не затирая локальные pending-операции. Проверить две вкладки/два устройства одного пользователя, поздние изменения и tombstones. Если существующего протокола недостаточно, сначала представить отдельный проект изменения RPC/схемы на согласование; RLS и миграции автоматически не менять.
3. **Конфликты и резервная копия.** Сохранять локальную и серверную версии, показывать различия и явный выбор пользователя, не «воскрешать» удалённый подход. Добавить валидируемый импорт личного версионируемого JSON поверх существующего экспорта, проверку владельца и повреждённого/чужого файла; очередь при выходе должна оставаться доступной только прежнему владельцу. Тестировать round-trip и отказ без частичного применения.
4. **Release gate.** На обычном HTTPS выполнить полный браузерный сценарий Auth → офлайн → перезапуск → reconnect → второй профиль/устройство → экспорт/импорт и прямые A/B/anon проверки только там, где их требует изменённый контракт. Проверить мобильные 360/390 px, консоль, статусы, Pages после публикации нужного коммита и предупреждение об отсутствии email recovery. До этого PR/пилот не считать готовыми к выпуску.

Каждый шаг заканчивается lint, typecheck, unit/integration тестами, build и `git diff --check`. Не использовать удалённые пароли A/B, не открывать регистрацию ради повторения уже завершённых проверок и не расширять доверие CA или отключать TLS.

## Required
1. Idempotent sync RPC, owner-bound operation ledger, server-owned revisions, compare-and-swap и tombstones; retry after unknown server ack.
2. Transactional outbox recovery, backoff/jitter, manual Sync, зависимость родителей/дочерних записей, multiple edits per entity.
3. User-scoped local data; офлайн только после прошлой успешной авторизации и без явного signout. Никакого offline-first-time-login.
4. Logout with pending warning + recovery/export path; недопустим cross-account replay/outbox visibility.
5. Concurrent edits на двух устройствах: обе версии сохраняются, пользователь выбирает. Удалённый подход не «воскресает».
6. Auth режим закрытого пилота: email/password, `Confirm Email OFF`, signup закрыт **после** первоначальной регистрации A. Проверить повторный вход A и серверный запрет новых регистраций. Email reset/verification не выдавать за готовые функции.
7. Версионируемые JSON export/import + тест плохого JSON, без secret leaks.
8. RLS/grants direct REST/RPC tests User A/B/anon, включая чужие ссылки.
9. Ручное тестирование PWA на телефоне 360/390px, офлайн перезапуск, возврат сети, GitHub Pages deployment.

## DoD — must all pass
- A сохраняет >=3 подходов офлайн, закрывает/открывает приложение, при reconnect отправляет ровно один раз.
- Offline first login и signed-out offline journal недоступны; другой аккаунт не может прочитать локальную историю A.
- RLS/REST A/B/anon; account switch блокирует cross-user visibility/dispatch.
- Conflict UI и tombstones; без потери данных после повторной отправки при неполученном ответе сервера.
- Backup round-trip и corruption тест; история в облаке доступна A на втором устройстве.
- Ссылка Pages доступна, но неавторизованный пользователь не получает доступ к данным; signup после закрытия реально запрещён сервером.
- Рабочий вход/выход и явное предупреждение о **недоступном восстановлении через почту**. Владелец лично проверил на устройстве и знает ограничение по восстановлению.

## Отдельный gate для открытой регистрации
До публичного multiuser запуска необходимо новый ADR: рабочая проверка email и восстановление (SMTP) **или** согласованный OAuth, защита от злоупотреблений, тестирование ранее автоматически подтверждённых пользователей, доступность входа и восстановление на настоящем Pages URL. Этот gate не входит в Plan 004.
